# Декомпозиция feature flags платформы на сервисы

## Бизнес-возможности и поддомены


| Бизнес-возможность                                  | Поддомен   | Почему                                                             |
| --------------------------------------------------- | ---------- | ------------------------------------------------------------------ |
| Управление флагами и черновиками                    | core       | Без этого платформа не сможет создавать и менять флаги             |
| Версионирование, публикация и rollback              | core       | Изменения нужно безопасно выпускать и при необходимости откатывать |
| Настройка rollout и вариантов эксперимента          | core       | Это основной сценарий feature flags и A/B-экспериментов            |
| Вычисление состояния для контекста пользователя     | core       | За этим результатом потребители и обращаются к платформе           |
| Проверка типизированных JSON конфигов               | supporting | Проверка помогает не опубликовать неверный конфиг                  |
| Просмотр истории изменений                          | supporting | История нужна для разбора изменений и ошибок                       |
| Идентификация пользователей админки и проверка прав | generic    | Это типовая задача, не связанная напрямую с флагами                |




## Карта сервисов


| Сервис                | Ответственность                             | Владение данными                                                        | Почему high cohesion                                                          |
| --------------------- | ------------------------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Configuration Service | Создаёт, проверяет и публикует конфигурацию | Флаги, JSON схемы, черновики, полные версии, варианты и правила rollout | Всё связано с переходом от черновика к опубликованной версии                  |
| Delivery Service      | Возвращает состояния, варианты и конфиги    | Копия активной версии флага и кеш результатов                           | Здесь находится только информация для чтения, без редактирования и публикации |
| History Service       | Сохраняет и показывает историю изменений    | Записи об изменении: действие, автор, время, версия                     | Он только записывает и читает историю, но не меняет флаги                     |
| Auth Service          | Проверяет пользователя админки и его права  | Пользователи админки, роли и права                                      | Учётные записи и права никак не зависят от флагов                             |


Полные версии остаются у Configuration Service, потому что они нужны для
rollback. History Service хранит только сведения об изменениях и не становится
вторым источником конфигурации.

## Проверка cohesion и coupling

**High cohesion.** У каждого сервиса одна понятная задача. Configuration Service
меняет флаги, Delivery Service обслуживает чтение, History Service показывает
прошлые изменения, а Auth Service работает с пользователями и правами.

**Low cohesion — антипример.** Один общий сервис, который одновременно редактирует флаги, обслуживает частые запросы, управляет пользователями и строит историю. Такой сервис пришлось бы менять в связи с любыми несвязанными доработками. (Нам не нравится)

**High coupling — риск.** Если Delivery Service читает таблицы Configuration
Service напрямую, любое изменение таблиц может сломать путь чтения. Та же
проблема появится, если History Service начнёт строить историю из чужой базы.

**Low coupling — решение.** После публикации Configuration Service передаёт полную версию по контракту `PublishedConfiguration`. Delivery Service сохраняет её у себя и не ходит в чужую базу. History Service получает событие `ConfigurationChanged`. Общей базы данных у сервисов нет.

## Диаграмма декомпозиции

```mermaid
flowchart LR
    admin_user([Пользователь админки])
    consumer[Система-потребитель]
    identity[Auth Service]

    subgraph platform[Feature flags platform]
        configuration[Configuration Service]
        delivery[Delivery Service]
        history[History Service]
        auth_contract[AuthorizationPort<br/>(пример DIP)]

        configuration -->|PublishedConfiguration| delivery
        configuration -->|ConfigurationChanged| history
        configuration -->|Проверяет право через| auth_contract
    end

    admin_user -->|Управляет конфигурацией| configuration
    admin_user -->|Запрашивает историю| history
    consumer -->|Запрашивает флаги и конфиги| delivery
    identity -.->|Реализует контракт| auth_contract
```



Внутри границы платформы находятся три сервиса. `Auth Service` показан снаружи
как generic-зависимость, а `AuthorizationPort` — это контракт.

`PublishedConfiguration` содержит номер версии, флаги, типизированные
JSON-конфиги, варианты и правила rollout. `ConfigurationChanged` содержит
действие, автора, время и номер версии.

## Пример DIP

При публикации Configuration Service обращается к контракту `AuthorizationPort`
и не знает, как именно устроена проверка прав. Реализация контракта вызывает
Auth Service. Если способ проверки поменяется, сценарий публикации переписывать
не придётся.

(На уровне сервисов `PublishedConfiguration` по идее тоже можно считать примером DIP, т.к. Delivery Service зависит от контракта `PublishedConfiguration`, а не от
реализации Configuration Service и его хранилища.)
