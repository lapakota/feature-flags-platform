# Масштабирование данных

## Данные и хранение

У `Configuration Service`, `Delivery Service` и `History Service` свои базы
PostgreSQL. Все флаги, настройки rollout и JSON-конфиги одной версии хранятся
в одном поле типа JSONB. Номер версии и `configurationId` — в отдельных полях.

Рост за `365 дней` рассчитан по [примеру нагрузки](23-server-caching.md#частота-и-стоимость-чтения),
без удаления старых версий и истории. Для изменяемых данных взята верхняя оценка:
в расчёте каждое сохранение считается новой записью. Обновление существующей
записи число строк не увеличивает.

| Данные                               | Хранилище                                            | Согласованность                                                                  | Серверный кеш                                   | Рост записей за год                                                                         |
| ------------------------------------ | ---------------------------------------------------- | -------------------------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Черновики, JSON-конфиги и схемы      | База `Configuration Service`                         | ACID + CP, `0 с` после сохранения                                                | Нет                                             | До `18 250`; существующие черновики обновляются на месте.                                   |
| Опубликованные версии                | База `Configuration Service`                         | ACID + CP, `0 с` после публикации                                                | Нет                                             | `10 × 365 = 3 650` версий, включая откаты.                                                  |
| Активная копия и рассчитанные ответы | Копия — база `Delivery Service`; ответы — память Pod | BASE + AP при потере связи с управлением; доставка до `5 минут` для `99%` версий | Cache-aside, ключ с версией, LRU, TTL `45–60 с` | До `3 650` копий новых конфигураций. Обновление заменяет копию; ответы в БД не сохраняются. |
| История изменений                    | База `History Service`                               | BASE + AP, цель — обновление за `60 с`                                           | Нет                                             | `3 650` записей.                                                                            |
| Статус применения версии             | Поле в записи версии в базе `Configuration Service`  | BASE + AP, цель — обновление за `60 с` после применения                          | Нет                                             | `0` отдельных строк: статус хранится в записи версии.                                       |
| Учётные записи, роли и доступ        | Хранилище внешнего `Auth Service`                    | ACID + CP, `0 с` после изменения прав                                            | Нет                                             | До `365` новых учётных записей или назначений ролей.                                        |
| Ключи API и разрешения               | База `Delivery Service`                              | ACID + CP, `0 с` после отзыва                                                    | Нет                                             | До `365` новых ключей.                                                                      |

## Шардирование

На старте шардирование не нужно: по расчёту выше версии и история добавляют
по `3 650` записей в год. Пока для них выбраны индексы.

| Ступень             | Решение                                                                                                                                                                                 |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Индексы             | Уникальный `(configurationId, version)` для версий; `(configurationId, occurredAt)` для истории; уникальные ключи для [защиты от повторов](15-interaction-model.md#защита-от-повторов). |
| Кеш                 | Частые запросы флагов обслуживает кеш `Delivery Service`. История пока остаётся без серверного кеша.                                                                                    |
| Реплики             | Пока нужны только для резерва. Читать историю с реплики можно, если доставка события и отставание реплики вместе укладываются в `60 с`.                                                 |
| Более мощный сервер | Если после оптимизации запросов всё ещё не хватает CPU, памяти или скорости диска.                                                                                                      |
| Шарды               | Если предыдущие меры не помогли и замеры показали, что конкретная база не справляется.                                                                                                  |

Решение пересматривается, если по прогнозу диск заполнится больше чем на `70%`
за ближайшие `12 месяцев` или при `10 000 запросов/с` стабильно получается
`p95 > 100 мс`. Сначала нужно найти причину, шардирование не включается автоматически.

## Репликация и карта размещения

У каждой из трёх баз — основная копия (лидер) и одна синхронная резервная
реплика на другом сервере. Все чтения и записи идут на лидера, включая проверки
ключей API и активной версии. Запись подтверждается только после сохранения
на основной и резервной копиях. Перед переключением на резервную копию
прежний лидер отключается от клиентских чтений и записей.

Карту размещения хранит сам сервис в настройках подключения: все ключи ведут
в одну базу — `shard-0`, к её текущему лидеру. Отдельный координатор не нужен.
За хранение и репликацию данных внешнего `Auth Service` отвечает его владелец.
