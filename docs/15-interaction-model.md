# Модель взаимодействия проекта

## Сценарии и выбор sync или async

| Сценарий и участники                                                                           | Модель | Обоснование                                            |
| ---------------------------------------------------------------------------------------------- | ------ | ------------------------------------------------------ |
| Админка через API Gateway → `Auth Service`: вход и обновление токена                           | Sync   | Без токена нельзя обратиться к защищённым API          |
| `Configuration Service` → `Auth Service`: право на публикацию или rollback                     | Sync   | Проверка должна завершиться до создания версии         |
| Система-потребитель → `Delivery Service`: состояния флагов и конфиги                           | Sync   | Данные нужны для текущего запроса                      |
| Админка → `Configuration Service`: список и страница флага                                     | Sync   | Пользователь ждёт данные на экране                     |
| Админка → `History Service`: история изменений                                                 | Sync   | Пользователь ждёт историю на экране                    |
| Админка → `Configuration Service`: сохранение черновика и настройка rollout                    | Sync   | Нужно сразу подтвердить сохранение                     |
| Админка → `Configuration Service`: публикация или rollback                                     | Sync   | Нужно вернуть номер новой версии или ошибку            |
| `Configuration Service` → `Delivery Service`: PublishedConfiguration                           | Async  | Применение настроек не задерживает ответ на публикацию |
| `Configuration Service` → `History Service`: ConfigurationChanged                              | Async  | Запись истории не задерживает публикацию               |
| `Delivery Service` → `Configuration Service`: уведомление о переключении на новую конфигурацию | Async  | Статус обновляется отдельно от запроса публикации      |
| Админка → `Configuration Service`: статус публикации                                           | Sync   | Экрану нужен текущий статус                            |

Админка и система-потребитель обращаются к сервисам через API Gateway.
Схема приведена в [описании API Gateway](./12-api-gateway-bff.md).

## Координация и брокер

Оркестрация нужна при публикации и rollback: `Configuration Service` сначала проверяет права и настройки, затем сохраняет версию. При ошибке проверки версия не создаётся.

После сохранения — хореография. Применение настроек и запись истории независимы, поэтому сбой `History Service` не мешает `Delivery Service`. Статус «Active» выставляется, когда `Delivery Service` сообщает, что новая конфигурация уже используется для расчёта флагов.

`RabbitMQ` даёт каждому получателю отдельную очередь и повторную доставку при сбоях. Очереди сохраняются после перезапуска брокера, сообщения записываются на диск. Отправитель ждёт подтверждения их приёма. Число попыток обработки ограничено, затем сообщение уходит в очередь ошибок.

Минусы: настройки применяются с задержкой, возможны дубли. Нужно обслуживать брокер, следить за очередями и разбирать ошибки обработки.

## Защита от повторов

| Операция                                                            | Ключ                                                         | Где хранится отметка                                                                | При повторе                                              |
| ------------------------------------------------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------------- | -------------------------------------------------------- |
| Публикация или rollback                                             | Пользователь + конфигурация + вид операции + Idempotency Key | БД `Configuration Service`: уникальная запись с ключом, телом запроса и результатом | То же тело — прежний результат; другое — 409             |
| Переключение `Delivery Service` на новую конфигурацию               | eventId                                                      | БД `Delivery Service`: обработанные события и активная версия                       | Дубли и версии с меньшим или равным номером пропускаются |
| Запись истории                                                      | eventId                                                      | БД `History Service`: запись с уникальным eventId                                   | Вторая запись не создаётся                               |
| Обновление статуса публикации после переключения `Delivery Service` | configurationId + version                                    | БД `Configuration Service`: статус указанной версии                                 | Новые версии не затрагиваются; повтор ничего не меняет   |

Проверка версии, сохранение результата, отметки обработки и исходящих сообщений выполняются в одной транзакции БД сервиса, в том числе и уведомления от `Delivery Service`. После сохранения результата сервис сообщает брокеру, что сообщение обработано. При повторной отправке eventId не меняется.

Rollback создаёт версию с новым, большим номером и настройками из выбранной старой версии.

Для GET запросов списка флагов/полной информации о флаге ключ не нужен: запрос не меняет данные.
