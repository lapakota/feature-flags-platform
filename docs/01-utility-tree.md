## Сценарии



### S1. Пиковая нагрузка на API — (H, H)

При обычной работе системы-потребители запрашивают состояния флагов через API.
Контур чтения берёт опубликованную конфигурацию из кеша; контур управления в
обработке запроса не участвует.

Мера: при `10 000` запросов в секунду `p95 ≤ 100 мс`.

### S2. Недоступен контур управления — (H, M)

Админка и API управления недоступны. API чтения продолжает возвращать последнюю
опубликованную конфигурацию.

Мера: при сбое длительностью `60 минут` доступность чтения остаётся не ниже
`99,9%`.

### S3. Повторное назначение варианта — (H, M)

Система несколько раз запрашивает один флаг для пользователя с одним и тем же
стабильным идентификатором. Затем сервис увеличивает rollout на один
процентный пункт. Пользователи, для которых флаг уже был включён, остаются в
прежней группе.

Мера: результат совпадает в `100%` из `10 000` повторных вычислений; переход
`10% → 11%` сохраняет всю исходную группу и добавляет следующий `1%`.

### S4. Rollback опубликованной версии — (H, M)

Платформа публикует rollback как новую версию и передаёт её в контур чтения.

Мера: новая конфигурация становится доступна через API за `≤ 5 минут`.

### S5. Публикация без необходимого права — (H, M)

Пользователь может редактировать черновик, но не имеет права сделать его активной конфигурацией. API управления отклоняет публикацию и сохраняет попытку в истории действий. (а также вызывает участкового)

Мера: неразрешённая публикация не изменяет активную конфигурацию, а причина отказа возвращается пользователю.

### S6. JSON не соответствует типу — (H, L)

Пользователь пытается опубликовать JSON-конфиг, который не соответствует
объявленной структуре. Публикация не проходит проверку.

Мера: некорректный конфиг не попадает в активную версию, а ответ содержит
описание несовместимых полей.
