# Рендеринг админки

## Модель рендеринга

Для админки выбран CSR. Здесь редактируют типизированный JSON, сравнивают версии,
публикуют настройки и делают откат. Важно, чтобы после загрузки интерфейс быстро
реагировал на действия и не требовал перезагрузки страницы. Для этих сценариев
всё равно нужен клиентский код, а отдельный сервер для SSR пока не нужен.
Админка доступна только после входа, SEO ей тоже не требуется.

Требования `10 000 RPS` и `p95 ≤ 100 мс` из [дерева полезности](./01-utility-tree.md)
относятся к Delivery Service, а не к админке. На выбор её рендеринга они не влияют.
Отдельного требования к отклику админки там пока нет. Для неё ориентир —
`INP ≤ 200 мс` минимум в 75% посещений: интерфейс должен быстро отвечать на ввод
в редакторе, выбор версий и нажатия кнопок. CSR сам по себе этого не гарантирует.
Время публикации на сервере оценивается отдельно.

## Code splitting

- Страница `/flags/:id/edit` загружается отдельно вместе с редактором
  типизированного JSON-конфига. На экране списка флагов этот код не нужен.
- Компонент сравнения на странице `/flags/:id/history` загружается после выбора
  двух версий. Сам список версий открывается без кода для просмотра diff.

## Ожидаемый эффект

Замеров пока нет. Оценка такая: если с редактором и diff в общем пакете LCP списка
флагов будет около `3 с`, то после разделения кода ожидается около `2,5 с`.
Экрану нужно загрузить и выполнить меньше JavaScript, но реальный выигрыш ещё
предстоит проверить.

Для проверки нужны несколько загрузок с пустым кешем до и после разделения кода:
на одном устройстве, с той же сетью и набором флагов. После замеров примерные
значения заменяются фактическими.

TTFB почти не изменится: сервер отдаёт тот же статический HTML, а разделение кода
влияет на загрузку JavaScript уже после ответа.

При первом открытии редактора или сравнении версий придётся подождать загрузки
их кода. Это время проверяется отдельно от LCP списка флагов и INP.
