# Итоговое архитектурное решение

Основные требования — быстрое чтение флагов, безопасная публикация и откат,
стабильный rollout и проверка JSON-конфигов.
[Подробнее о требованиях](README.md#архитектурные-драйверы).

## Итоговая архитектура

| Часть                      | Решение и причина                                                                                                                                                                                                                                                                                                                                 | Подробности                                                                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Декомпозиция               | Управление, чтение и история работают отдельно. Выдачу флагов можно масштабировать независимо от редактирования, а история не меняет конфигурацию. Админка — одно приложение с FSD.                                                                                                                                                               | [Сервисы](03-service-decomposition.md), [ADR](adr/0001-separate-management-and-delivery.md), [фронтенд](07-frontend-architecture.md). |
| Взаимодействие и доступ    | Запросы идут через API Gateway. Проверки и сохранение выполняются синхронно; доставка версии и запись истории — через RabbitMQ. Повторный запрос публикации с тем же ключом не создаёт дубль, права проверяются в сервисах.                                                                                                                       | [Шлюз](12-api-gateway-bff.md), [взаимодействия и контракты](15-interaction-model.md), [доступ](16-authentication-authorization.md).   |
| Надёжность и наблюдаемость | При сбое управления чтение продолжает отдавать последнюю полученную версию. Если API недоступно, потребитель использует значения по умолчанию. Для сбоев предусмотрены реплики сервисов, таймауты, повторы с лимитом попыток и очередь ошибок. Цели чтения: `99,9%` успешных запросов, p95 до `100 мс`. Доставка — за `5 минут` для `99%` версий. | [Kubernetes](17-kubernetes.md), [тактики](19-reliability.md), [метрики и алерты](20-reliability-observability.md).                    |
| Данные                     | У внутренних сервисов отдельные базы PostgreSQL с резервными репликами, пока без шардирования. При редактировании и проверке прав нужны актуальные данные; копии могут обновляться с задержкой. Кеш в памяти Pod ускоряет выдачу флагов. Права и активный номер версии не кешируются.                                                             | [Согласованность](22-data-consistency.md), [кеш](23-server-caching.md), [масштабирование](24-scaling.md).                             |

Общая схема — [C4 Containers](views/c4-container.md), границы платформы —
[C4 Context](views/c4-context.md).
