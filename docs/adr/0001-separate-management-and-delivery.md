# 0001. Разделить управление и чтение флагов

- **Status:** Accepted
- **Date:** 2026-07-27
- **Deciders:** Самошкин Артём

## Context

Самый простой вариант — один сервис для управления и чтения. Но тогда сбой во
время редактирования или публикации флагов затронет и обычные запросы. При этом
флаги и конфиги читаются гораздо чаще, чем изменяются.

## Decision

Разделить платформу на два приложения:

- API управления работает с черновиками, проверяет типы JSON-конфигов, публикует
версии и хранит историю изменений;
- API чтения получает опубликованную версию, кеширует её, вычисляет состояния
флагов для переданного контекста и возвращает конфиги.

Публикация создаёт новую версию конфигурации. Rollback также создаёт новую
версию, повторяющую выбранное рабочее состояние.

Rollout задаётся целым процентом от `0%` до `100%` с шагом `1%`. При увеличении
процента ранее включённая группа сохраняется.

## Consequences

**Что выигрываем.** Нагрузку на чтение можно масштабировать отдельно. При сбое
API управления потребители продолжают получать флаги. Каждый ответ строится по
одной версии конфигурации.

**Чем платим.** Новая конфигурация появляется в API чтения с задержкой. Также
нужно следить за обновлением кеша.

**Что отвергли.** Единый сервис, который читает актуальную конфигурацию на каждый
запрос. Он проще, но становится общей точкой отказа для управления и чтения.
